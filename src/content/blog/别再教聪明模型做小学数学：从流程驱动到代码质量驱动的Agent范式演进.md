过去一年，我在 AI 编程这件事上绕了一个不小的圈。

最开始，我很喜欢给 Agent 加流程。

需求先澄清，澄清完写 Spec；Spec 确认之后拆 Tasks；开始改代码之前先出计划；改完再 Review，再验证，再归档。项目里的 Skills 越来越多，规则越来越细，甚至连模型在什么阶段应该输出什么格式，我都希望提前规定好。

当时这么做有很充分的理由。

早期模型确实经常乱来：看到一个报错就直接改，找到一个调用点就以为找到了根因，任务稍微长一点就开始丢目标。给它一条明确的轨道，往往比让它自由发挥稳定得多。

问题是，模型变了，而我的使用方式没有及时变。

后来我逐渐发现，有些过去很有价值的“护栏”，在更强的模型上反而开始产生摩擦。模型花很多篇幅写计划、填模板、汇报阶段进度，最后交出来的代码却未必因此更好。

也是在这个过程中，我意识到另一个比工具选择更麻烦的问题：

> **我把太多本该属于自己的思考也一起外包了。**

---

## 一、真正让我警觉的，不是 AI 写错代码

以前写代码，我脑子里会自然走一遍这样的过程：

> **理解问题 → 建模 → 想方案 → 写代码 → 调试 → Review**

用了很长一段时间 AI 之后，这个循环一度变成了：

> **描述需求 → 等 AI 生成 → 看能不能跑 → 下一个需求**

刚开始没觉得有什么问题。

毕竟代码确实写得更快，很多重复劳动也消失了。

但过了一段时间，我发现自己读代码的状态变了。

以前看到一段陌生实现，我会下意识去想：

- 数据从哪里来；
- 状态在哪里发生变化；
- 为什么这里要多这一层；
- 哪些地方可能违反前置条件；
- 如果这里出错，影响会往哪里传。

后来面对 AI 一次生成的大段代码，我很容易直接进入一种被动阅读状态。

只要测试绿了，第一反应居然会变成：

> **应该差不多吧。**

这其实挺危险。

真正退化的不是某个 API 记不住了，而是主动建立系统模型的习惯在变弱。

编程不只是“知道语法”和“记得框架怎么用”。大量能力都来自长期形成的模式识别：看到一个状态流就知道哪里可能失控，看到一个类承担了太多职责就会觉得别扭，看到异常处理出现在奇怪的位置就会继续往上追。

这些能力不用，同样会生疏。

所以后来我给自己定了一条很简单的边界：

> **AI 可以替我写很多代码，但我不能不知道这些代码为什么应该这样写。**

样板代码可以让它生成，批量修改可以让它做，重复劳动当然也没必要自己硬敲。

但几个问题我必须能回答：

- 这个功能真正的不变量是什么？
- 关键状态在哪里流转？
- 这次修改碰到了哪些边界？
- 为什么选择这个方案，而不是另一个？
- 如果它错了，我有没有能力看出来？

这比“代码是不是我亲手敲的”重要得多。

## 二、很多重流程，本来就是为旧模型准备的

回头看那些复杂的 Agent 工作流，我并不觉得它们“从一开始就是错的”。

恰恰相反，它们当时解决的都是真问题。

模型容易局部修改，就要求它先搜索。

模型不会规划，就让它先写 Plan。

模型容易忘目标，就把工作拆成 Tasks。

模型修改之后不验证，就强制增加 Review 和 Test 阶段。

从工程角度看，这很合理：

> **模型内部做不好的事情，就暂时用外部流程补。**

于是我们慢慢有了各种不同形式的东西：

```text
需求
→ Spec
→ Design
→ Tasks
→ Implement
→ Review
→ Verify
→ Archive
```

有些工具更偏规格管理，有些更偏执行工作流，也有一些会用 Schema、状态文件甚至脚本，把每一步都固定下来。

在模型规划能力比较弱的时候，这类方法能明显降低随机性。

但这里有一个经常被忽略的问题：

> **工作流补偿的是模型当时的能力，而模型能力本身一直在变。**

现在的强模型已经能自己完成不少过去必须显式提示的动作：

- 搜索代码；
- 沿调用链继续追踪；
- 根据测试失败调整判断；
- 在实现过程中发现原方案不成立之后重新规划。

这并不意味着它已经不会犯错。

它当然还会犯，而且长任务、跨上下文任务依然很难。

但问题的性质已经变了。

以前更像是：

> 不告诉它下一步做什么，它很可能不知道下一步做什么。

现在很多时候则变成：

> 它其实知道该怎么查，但我们要求它先完成一套规定动作。

这两者不是一回事。

## 三、我为什么开始减少工作流指令

我真正开始怀疑重流程，是因为碰到过很多次类似的情况：

> **Agent 的过程越来越“专业”，结果却没有同步变好。**

它会输出很漂亮的计划。

会列风险。

会写 checklist。

会逐项告诉你某个阶段已经完成。

看起来一切井井有条。

但打开代码一看，真正的问题可能还在那里。

后来我觉得，这里面至少有三个原因。

### 1. 上下文不是免费的

模型的上下文越来越长，这是事实。

但长上下文不等于“往里面塞什么都没有代价”。

假如一个任务开始之前，模型已经要读：

- 很长的工作流说明；
- 固定输出模板；
- 状态迁移规则；
- Skill 使用协议；
- 多 Agent 协作约定；
- 各种重复的 MUST / MUST NOT。

这些东西就会和真正重要的信息混在一起：

- 业务规则；
- 类型定义；
- 调用关系；
- 测试；
- 历史兼容逻辑；
- 系统不变量。

我现在不太追求“让模型知道尽可能多”。

我更在意的是：

> **当前上下文里的信息，有多少是真的和这个任务有关。**

很多时候，一份短但准确的项目说明，加上正确的代码入口，比几千 Token 的通用工作流更有用。

---

### 2. 软件排障本来就不是线性的

实际写代码的时候，很少真的按照一条直线走到底。

你可能先看到一个 API 报错，追进去之后发现不是 API 的问题，而是共享类型定义错了。

也可能看起来是状态管理的问题，最后发现根因只是某个边界没有维护不变量。

有时候应该先跑测试。

有时候甚至不用跑，先把同类实现搜出来就已经能确认设计意图。

真正有效的探索路径往往是：

> **看一眼 → 得到新证据 → 改变方向 → 再验证**

这本质上是一棵动态展开的搜索树。

如果外部流程规定模型：

> 先完整分析  
> → 再生成设计  
> → 再拆任务  
> → 再逐项实施

就可能出现一种很奇怪的情况：

为了遵守流程，模型不得不把一个原本十分钟能确定的问题，写成一套半小时的工作报告。

流程本来是为了减少无效动作，最后自己却成了无效动作的一部分。

---

### 3. 过程完成，不等于工程完成

这是我现在最在意的一点。

流程一旦太重，Agent 很容易开始优化一个错误目标：

> **怎样顺利完成当前阶段？**

而不是：

> **怎样让系统恢复到正确状态？**

这时候就很容易出现一些熟悉的代码味道。

比如本来应该追根因，最后却加了几个 fallback，把异常状态藏起来。

本来应该拆开职责，最后因为“当前文件改起来最方便”，直接把业务逻辑塞进 Controller。

或者一个简单函数就能解决的问题，为了让设计显得完整，又多出 Factory、Adapter、Manager 之类的一层。

代码能跑。

任务卡也打勾了。

但架构比修改之前更差。

所以现在我看 Agent 输出，越来越少关心它有没有漂亮地执行完流程，反而更关心几个朴素的问题：

> 根因到底解决了吗？  
> 系统不变量还成立吗？  
> 修改有没有制造新的债务？  
> 证据在哪里？

---

## 四、与其规定路径，不如把结果标准说清楚

这也是我现在最大的使用变化。

以前我喜欢告诉模型：

> 第一步做什么。  
> 第二步做什么。  
> 第三步输出什么。

现在我更倾向于告诉它：

> 什么东西不能破坏。  
> 什么条件必须满足。  
> 什么结果才算完成。

两者的区别很大。

| 维度 | 过程编排 | 质量约束 |
| --- | --- | --- |
| 重点 | 模型怎么执行 | 最终结果是否正确 |
| 上下文 | 流程、模板、状态 | 业务、代码、不变量 |
| 模型自主性 | 较低 | 较高 |
| 人类职责 | 审批过程 | 判断边界和风险 |
| 可靠性来源 | Prompt | 类型、测试、静态检查、CI |

比如我不太在意模型到底：

- 先搜文件还是先跑测试；
- 先改类型还是先改实现；
- 是否中途推翻了原来的判断。

这些都可以根据实际情况调整。

但下面这些事情，不能靠“自由发挥”：

- 不能悄悄破坏公共 API；
- 不能为了消灭异常绕开系统不变量；
- 不能让类型安全倒退；
- 不能没跑测试却说“已经验证”；
- 修复 Bug 之后最好留下可以复现问题的回归证据。

我的理解逐渐变成了：

> **模型负责寻找路径，工程系统负责判断这条路径最后有没有走对。**

## 五、能交给工具检查的东西，就别只写在 Prompt 里

这件事想明白之后，我对 `AGENTS.md` 的看法也变了。

以前很容易把所有规则都塞进去：

> 不允许循环依赖。  
> 不允许跨层调用。  
> 某模块不能依赖某模块。  
> API 必须兼容。  
> DTO 必须满足某种结构。

这些话不是没用。

问题在于，Prompt 从来都不是最可靠的约束执行器。

模型可能漏掉，也可能误解，还可能觉得“这里特殊，可以例外”。

所以现在我的原则是：

> **只要规则能够机器验证，就尽量不要只靠模型自觉。**

类型问题，让类型系统报错。

格式和静态问题，让 linter 拦。

架构边界，能写 architecture test 就写 test。

行为正确性，用 unit test、integration test、contract test、e2e test 去验证。

真正不能退让的东西，最后放进 CI。

这样一来，`AGENTS.md` 就不用承担一个不现实的职责：

> 靠一大段文字保证模型永远不犯错。

它更适合做几件事：

- 告诉模型这个项目怎么看；
- 说明真正重要的系统边界；
- 写清楚哪些决策风险太高，不能擅自拍板；
- 告诉它应该运行哪些验证。

我现在更喜欢把它理解成一个项目级的**工程地图**，而不是模型操作说明书。

## 六、不要要求 Agent“看完整个项目”

我以前还写过另一类规则：

> 修改之前必须完整扫描相关代码。

初衷很简单：防止模型看到一个局部报错就开始乱改。

后来发现，“完整”这个词本身就有问题。

尤其是在 monorepo 里。

什么叫完整？

读 10 个文件算完整，还是 50 个？

要不要把所有间接调用者都展开？

要不要把历史兼容代码也全部读一遍？

如果为了避免局部近视，强迫模型把大量相关性很低的文件一股脑塞进上下文，反而又回到了前面的上下文污染问题。

所以我现在更倾向于要求一个东西：

> **最小充分系统模型。**

意思很简单。

Agent 不需要知道整个项目，但它至少得知道：

- 当前入口在哪里；
- 关键调用链怎么走；
- 数据或状态怎么流；
- 直接上下游是谁；
- 哪些类型会被影响；
- 哪些测试能证明行为；
- 当前依赖哪些系统不变量；
- 有没有已有的同类实现。

什么时候可以停止继续搜？

我觉得不是“相关文件全部看完”的时候。

而是它已经能比较有把握地回答：

> 这个问题为什么发生？  
> 真正的根因在哪里？  
> 我准备做的修改会影响哪些地方？

如果后面又出现新证据，再继续往外追。

这比无限扫描更实用。

## 七、人类应该介入风险，而不是介入每一步

以前我的规则还有一句：

> 开始修改之前，先输出方案，等我确认。

现在看，这也太绝对。

如果只是：

- 修一个明显的局部 Bug；
- 修类型错误；
- 补一个已有模式下的测试；
- 改一个局部实现；
- 修 typo。

每次都要：

> **分析 → 写报告 → 等审批 → 修改**

Agent 很快就退化成了一个需要不断签字的远程实习生。

这不是我想要的效果。

我现在更倾向于按风险分级。

普通的、低风险的修改，可以直接：

> **理解 → 修改 → 验证 → 汇报**

真正需要停下来问人的，是另外一类事情：

- 修改公共 API；
- 数据库迁移；
- 改变持久化数据语义；
- 调整认证或权限；
- 跨模块重构；
- 删除大量现有代码；
- 存在几个代价完全不同的方案；
- 代码本身无法告诉模型产品应该怎么选；
- 实际影响范围已经明显超出最初任务。

这些事情的问题不是“模型够不够聪明”。

而是它们本身包含业务判断、风险取舍，或者不可逆成本。

这才是人真正应该介入的地方。

## 八、我现在放在项目里的 `AGENTS.md`

现在这份文件，我已经不再把它写成一条固定流水线。

它主要管四件事：

1. 开始修改之前，至少应该理解到什么程度；
2. 项目的基本工程底线是什么；
3. 哪些事情风险太高，需要升级给人；
4. 最后必须拿什么证据证明改动有效。

下面是目前的版本：

```markdown
# AGENTS.md

## 目标

在保证正确性、可维护性和项目一致性的前提下，自主完成代码修改。

不要为了遵守固定流程而制造额外步骤。应根据任务复杂度选择最有效的探索、实现和验证路径。

---

## 一、修改前建立足够的系统理解

在修改代码之前，应先获得完成当前任务所需的最小充分上下文。

至少确认：

- 当前问题涉及的入口与主要实现；
- 直接上游与下游调用关系；
- 关键数据流、状态流与类型；
- 相关测试；
- 已有同类实现或公共能力；
- 受影响的系统不变量与模块边界。

不要因为找到第一个可疑位置就立即修改，也不要为了“完整”而无边界扫描整个代码库。

当已有证据足以解释问题机制、根因和影响范围时，可以停止扩展检索；如果后续出现新的依赖或证据，再继续向外追踪。

---

## 二、核心工程原则

### 1. 优先解决根因

不要通过 fallback、异常吞噬、重复 null check、默认值或兼容分支掩盖非法状态。

如果某种状态按照系统设计不应该出现，应优先追查其来源并恢复系统不变量。

### 2. 保持职责边界

函数、类和模块应承担清晰且有限的职责。

不要为了完成当前任务，把业务逻辑放进最方便修改的位置。

业务规则、数据访问、UI、协议转换、状态管理、缓存和日志应保持合理边界。

### 3. DRY，但避免错误抽象

真正共享业务语义、规则和变化原因的逻辑，应保持单一实现来源。

不要仅因为两段代码形式相似就强行抽象。

已有公共能力能够满足需求时，优先复用或完善，不要平行实现第二套机制。

### 4. KISS

优先选择简单、直接、容易理解和维护的实现。

不要为了理论上的灵活性、扩展性或“设计感”增加没有明确价值的抽象层、包装层或间接调用。

### 5. YAGNI

只解决当前存在的需求，以及能够从现有代码和产品约束中明确确认的扩展点。

不要为假设中的未来场景提前搭建复杂框架。

### 6. 保持类型安全

优先使用类型系统表达业务状态与约束。

避免不必要的 `any`、无约束对象、模糊字典、重复类型断言，以及本可由类型系统消除的运行时判断。

有限状态应优先使用联合类型、枚举或等价结构表达。

### 7. 维护系统不变量

明确哪些状态必须始终成立。

不要为了让当前路径“能跑”而绕开不变量。

能在边界处验证的约束，不要在内部每一层重复 defensive check。

错误应在最合理的边界被明确处理，不应静默忽略。

### 8. 保持命名和代码自解释

名称应尽可能表达真实业务语义。

避免无必要使用 `data`、`obj`、`tmp`、`item`、`value`、`handle`、`process` 等模糊命名，除非局部上下文已经足够明确。

不要用注释补救本来可以通过命名表达的含义。

### 9. 消除有业务语义的魔法值

具有业务含义的数字、字符串、状态、路径、阈值等，应通过命名常量、类型或配置表达。

不要为了形式上消灭字面量而创建没有语义价值的常量。

### 10. 设计模式按需使用

设计模式是解决问题的手段，不是目标。

如果简单函数、明确类型或现有模块就能解决问题，不要为了套用模式增加额外结构。

### 11. 尊重项目已有体系

修改前观察项目现有的目录结构、命名习惯、类型建模、错误处理、数据流、测试方式、模块边界和公共抽象。

没有充分理由时，不要引入第二套风格。

### 12. 控制修改范围

优先实现最小且完整的修改。

不要顺带进行与当前任务无关的大规模重构。

如果当前问题的根因就是重复实现、错误职责划分或公共抽象缺陷，可以进行必要重构，但应控制影响范围并说明原因。

---

## 三、风险升级

以下情况不要自行做不可逆决策，应先说明影响并请求确认：

- 修改公共 API 或外部协议；
- 修改数据库 Schema 或执行数据迁移；
- 改变持久化数据语义；
- 涉及认证、授权或安全边界；
- 大范围删除代码；
- 跨模块职责重构；
- 明显改变系统架构；
- 存在多个影响显著不同、无法仅从代码判断优劣的方案；
- 需要产品或业务决策才能确定行为；
- 实际修改范围明显超过原始任务。

普通局部修改无需机械等待确认。

---

## 四、验证要求

完成修改后，必须提供与修改相匹配的验证证据。

根据任务实际情况执行：

- 与修改直接相关的测试；
- 回归测试；
- typecheck；
- lint；
- 必要的 integration / contract / e2e tests；
- 项目已有的构建或验证命令。

修复 Bug 时，如条件允许，应增加能够复现原问题的回归测试。

涉及公共接口、共享类型或公共模块时，应检查主要下游调用方。

不得在未实际执行验证命令的情况下声称“测试已通过”“问题已解决”或“没有影响其他功能”。

如果某项验证无法执行，应明确说明未执行什么、原因是什么，以及仍然存在什么风险。

---

## 五、最终交付

最终汇报保持简洁，说明：

1. 问题根因；
2. 修改内容；
3. 为什么采用该方案；
4. 实际执行了哪些验证；
5. 是否存在剩余风险或未验证项。

不要为了展示过程而生成没有实际价值的大量阶段报告、模板或文档。

---

## 最终原则

优先级依次为：

1. 正确性；
2. 系统不变量；
3. 可验证性；
4. 清晰度；
5. 可维护性；
6. 与项目现有体系一致；
7. 最小必要复杂度。

不要把“尽可能通用”“尽可能防御”或“使用更多设计模式”当作优化目标。
```

## 九、Agent 工程不会消失，只是该换一个重心了

写到这里，容易产生一个误解：

既然我不喜欢重流程，是不是意味着 Agent Framework、Skills、Harness 都没用了？

不是。

我反而觉得这些东西会继续存在，而且会越来越重要。

只是它们更应该解决“系统问题”，而不是替模型模拟思考。

比如：

- 给 Agent 提供可靠的工具；
- 控制权限；
- 保存长任务状态；
- 提供代码和文档检索；
- 管理跨上下文任务；
- 连接测试环境；
- 执行 CI；
- 拦截高风险操作；
- 接入 Issue、Repo 和运行环境。

这些都是非常实际的工程价值。

我只是越来越不相信另一件事：

> **我们能靠不断增加 Prompt 流程，把一个 Agent 调教成永远按照预想方式思考。**

模型本身会继续变化。

今天需要额外提醒它做的事情，明天可能已经成了默认能力。

如果把太多“模型当前不会什么”的假设固化进工作流，迟早还得重新拆。

所以我现在更愿意让 Harness 管环境、工具、状态和验证。

至于具体怎么解决问题，尽量留给模型自己判断。

---

## 十、最后变化最大的，其实是工程师的位置

用了很久 AI 之后，我现在觉得工程师最不应该做的，是退化成 Prompt 流程管理员。

每天研究：

> 第一步该让模型输出什么？  
> 第二步要不要加一个确认？  
> 第三步要不要再套一层 Skill？

这些东西不是完全没价值。

只是随着模型能力提高，它们不应该继续占据最多的注意力。

真正值得工程师花时间的，还是那些老问题：

- 这个系统的边界划得对不对；
- 不变量有没有被表达清楚；
- 类型有没有反映真实业务状态；
- 测试验证的是不是关键行为；
- 模块职责有没有慢慢腐化；
- Agent 拿到的工具是否足够可靠；
- 一个错误修改能不能被自动拦下来。

AI 并没有让这些问题消失。

甚至恰恰相反。

代码生成越来越便宜之后，**判断什么代码值得进入系统**反而变得更重要了。

所以我现在理解的人机分工，大概是这样：

> **我负责知道我们到底在解决什么问题，也负责守住系统边界和工程标准。**
>
> **模型负责搜索、实现、试错，以及完成那些机器更擅长的大量执行工作。**
>
> **最后，再让测试、类型系统和 CI 给出尽可能确定的证据。**

这套方式不一定适合所有项目。

模型比较弱、任务极长、合规要求严格，或者团队本身需要强审计的时候，更明确的流程仍然有价值。

我反对的从来不是流程本身。

我真正想砍掉的是那些已经失去收益，却因为“以前一直这么做”而继续存在的流程。

## 结语

最近这段时间，我删掉了不少以前觉得“必不可少”的 Agent 规则。

删的时候其实还有点不放心。

总觉得少写一句，模型就会不会又开始乱来。

结果用了一阵之后，我发现真正影响结果的，往往不是有没有要求它先输出一份漂亮的 Plan。

更重要的是另外几件事：

- 它有没有拿到正确的上下文；
- 它知不知道哪些东西不能碰；
- 项目有没有足够好的测试；
- 错误的实现能不能被自动挡住；
- 最后，我自己到底看不看得懂它改了什么。

到这里，我对 AI 编程这件事的想法反而简单了很多。

别急着替一个越来越会思考的模型规定所有思考步骤。

先把自己的系统做好。

把边界说清楚，把不变量守住，把验证补齐。

剩下的路，让它自己找。

如果连错误的路都能被工程系统及时拦下来，我们也就没必要一直站在旁边告诉它：

> **第一步迈左脚，第二步迈右脚。**
